## 1. 中文术语与核心定义

本规范优先使用中文名称，英文只作为代码或架构映射参考。

- **学习能力目标（Objective）**：一个可以判断“用户能不能做”的具体能力目标。
- **学习证据（Learning Evidence）**：用户真实做过什么，以及该表现对某个学习能力目标说明了什么。
- **能力验证规则（Verification Contract）**：系统要看到什么样的学习证据，才有资格把某个学习能力目标判为“已掌握”。
- **新场景应用证据（Transfer Evidence）**：用户在没有直接照搬刚学示例的情况下，把同一知识或方法用于变化后的新问题。
- **学习证据视图（Evidence View）**：Learning Evidence System 对某个学习能力目标当前支持证据、冲突证据、缺口、独立程度与时间相关性的统一整理结果。
- **用户自述（User Claim）**：用户明确说“我会了 / 我不会 / 我不想验证”等主观声明。它影响路线与教学，但不等同于系统验证后的掌握事实。

硬原则：

> **能力验证规则的严格程度，由学习能力目标本身声称的能力强度决定。**

> **“已掌握”必须有与目标声明相匹配的真实证据，不能因为对话顺畅、Agent 鼓励或用户一句“懂了”自动产生。**

---

## 2. 能力目标分四层，不再把“会”混成一个词

V1 内部至少区分四类能力层次。

### 2.1 L1：知道 / 识别

典型目标：

- 能识别某概念；
- 能说出基本定义；
- 能判断一个直接事实。

通常一次有效识别或简短说明即可形成较强支持证据。

### 2.2 L2：理解 / 解释

典型目标：

- 能用自己的话解释；
- 能说明为什么；
- 能区分相似概念；
- 能指出关键因果关系。

通常需要自主解释、推理或比较证据。

费曼复述主要服务这一层。

### 2.3 L3：应用

典型目标：

- 能计算；
- 能实现；
- 能在标准场景中使用；
- 能根据案例作出正确判断。

至少需要一次真实应用表现，不能只靠解释。

### 2.4 L4：独立使用

典型目标：

- 能独立解决；
- 能排查；
- 能设计；
- 能综合运用；
- 能把知识用于变化后的问题。

锁定：

> **凡 Objective 声称“能独立使用 / 排查 / 设计 / 解决”，至少必须存在一次独立的新场景应用证据。**

“新场景应用证据”不等于必须做考试题，可以来自：

- 自然对话中的新例子；
- 新代码；
- 真实项目；
- 作业；
- Debug；
- 用户自己构造的例子；
- 用户发现并纠正 Agent 的错误。

如果真实任务本身已经是新场景，就不再额外制造“迁移题”。

---

## 3. 新场景不等于高难度

新场景的目标是减少“照着刚才答案复述”的可能性，而不是人为增加难度。

正确的新场景：

- 表面条件变化，但核心能力相同；
- 需要用户重新判断或迁移；
- 不直接复制刚讲过的原题。

错误做法：

- 为了验证基础二重积分，突然出竞赛级三重积分；
- 为了验证 Spring self-invocation，要求用户立即解决无关的复杂分布式事务问题。

硬原则：

> **迁移验证改变情境，不随意改变能力层级。**

---

## 4. 证据不足时允许“待验证”

Study Agent 不强迫所有目标立即二选一：

```text
已掌握 / 未掌握
```

推荐主状态继续保持：

```text
学习中
↓
待验证
↓
已掌握
↓
需要复习
```

“待验证”表示：

- 已经存在较强正证据；
- 但仍缺当前 Objective 的能力验证规则要求的关键证据。

例如：

```text
解释：强
标准应用：强
独立新场景：缺失
```

若 Objective 是“能独立排查”，此时应为“待验证”，而不是强行判“已掌握”或“不会”。

---

## 5. 用户可以跳过验证，但系统不能伪造掌握

用户拥有学习路线最终选择权。

用户可以说：

- “不用问我了，直接往下学。”
- “这个我会，先跳过。”
- “我只想快速看懂，不需要验证。”

系统应允许继续，不设置课程锁。

但后台必须区分：

```text
用户选择跳过 / 自述已会
```

和：

```text
系统已有充分证据确认掌握
```

用户拒绝验证时，可以继续路线；系统 mastery 不得因此自动升级。

---

## 6. “独立完成”必须考虑 Agent 帮了多少

只记录最终“答对 / 答错”会高估用户能力。

V1 锁定四级帮助程度：

```text
独立完成
轻提示后完成
明显引导后完成
答案给出后复述
```

代码可映射为类似：

```text
independent
light_hint
guided
answer_given
```

但产品与文档优先使用中文。

### 6.1 独立完成

Agent 没有提供当前问题的关键答案、关键方向或关键推理步骤。

可以支持“独立能力”结论。

### 6.2 轻提示后完成

Agent 只帮助缩小范围或提醒一般策略，没有泄露核心答案。

这是强学习证据，但单独不足以证明“独立使用”。

### 6.3 明显引导后完成

Agent 已提供关键中间步骤、关键概念或主要推理桥梁。

可证明“在帮助下能够完成”，不能证明独立解决。

### 6.4 答案给出后复述

Agent 已给出核心答案，用户随后正确复述。

可说明用户已经接触并可能形成初步理解，但不能证明应用或独立能力。

### 6.5 Agent 自己完成

如果 Agent 自己定位问题、修改代码、完成作业，而用户没有真实能力表现：

> **不产生用户能力证据。**

它只能产生材料、示例、建议或系统执行记录。

---

## 7. “独立”不等于闭卷

锁定定义：

> **独立完成不是“完全不使用外部资源”，而是用户没有获得针对当前问题的关键答案或关键推理路径。**

正常专业工具通常不破坏独立性，例如：

- 官方文档；
- 搜索；
- RAG 找资料；
- IDE；
- 编译器；
- 计算器；
- API Reference；
- 用户自己的笔记。

关键要区分：

```text
资料辅助
vs
解法辅助
```

### 资料辅助

帮助用户找到材料、源码、定义、接口或原始信息，通常不降低独立程度。

### 解法辅助

直接指出当前问题的关键方向、关键代码行、关键结论、算法步骤或答案，会降低独立程度。

例如 RAG 帮用户定位源码文件可以保持独立；Agent 直接说“问题就在某函数的 proxy bypass”则属于解法辅助。

---

## 8. 需要验证独立能力时，先给一次无关键提示机会

如果当前 Objective 的能力验证规则要求“独立”，Agent 必须先让用户自己尝试。

推荐流程：

```text
第一次独立尝试
↓
成功
→ 形成独立证据

失败
↓
判断错误类型
↓
给最小必要提示
↓
再次尝试
```

失败后应正常教学，不允许为了保住 Evidence 纯度而故意拒绝帮助用户。

后续可以换一个新场景，再给用户一次真正独立尝试的机会。

用户明确点“直接告诉我”或要求答案时，应立即教学；本轮后续不能伪装成独立验证。

---

## 9. 提示程度优先结构化记录，不全靠 LLM 事后猜

教学动作本身应尽量标记帮助类型，例如：

```text
clarification
resource_assistance
strategy_hint
key_step_hint
answer
```

Evidence System 可以据此推导帮助程度。

只有自然对话中难以结构化判断的情况，再由语义 evaluator 辅助分类。

硬原则：

> **能够在产生帮助动作时确定的信息，不应全部留给另一个 LLM 事后重新解释。**

---

## 10. 教学成功与能力验证成功不是一回事

Agent 的目标有时是：

> 帮用户学会。

有时是：

> 判断用户能否独立完成。

两者不能混为同一件事。

Agent 给足提示后用户成功，可能意味着教学很成功，但不能因此写入“用户独立掌握”。

锁定原则：

> **AI 教得好，不等于用户已经能够独立做到。**

---

## 11. 不设置“做对 N 次 = 掌握”

V1 不采用统一计数阈值：

```text
correct_count >= 3
→ mastered
```

原因：证据质量比次数更重要。

例如：

```text
10 次高度相似选择题全对
```

未必比：

```text
1 次真实新场景中独立分析、解释并正确解决问题
```

更能证明“独立使用”。

锁定：

> **证据质量优先于证据数量。**

---

## 12. 一次高质量成功可以非常强，但通常不孤立裁决

一次表现如果同时具备多数特征：

- 用户真实完成；
- 无关键答案提示；
- 场景不是刚讲过的原题；
- 猜测空间低；
- 有合理过程或解释；
- 最终结果正确；
- 没有明显矛盾表现；

可以成为非常强的单条 Evidence。

如果此前已经存在：

```text
解释证据：强
应用证据：强
独立新场景：强
近期强冲突：无
```

则不强制再刷第二、第三道题，可以直接支持“已掌握”。

但如果此前没有任何证据，只出现一次低信息量成功，例如二选一猜中，则通常不足以单独确认掌握。

---

## 13. 防止“蒙对”主要提高证据信息量，不机械增加题数

优先方法：

- 要求说明为什么；
- 让用户构造自己的例子；
- 改变表面情境；
- 观察解决过程，而不只看最终答案；
- 使用真实项目或真实代码；
- 避免高猜测概率的单一选择结果成为强证据。

硬原则：

> **最终答案正确，不自动等于过程有效。**

---

## 14. 只有“熟练 / 稳定”目标才默认要求重复与跨时间证据

如果 Objective 只是：

- 能识别；
- 能解释；
- 能应用；
- 能独立解决一次新场景；

不机械要求固定次数。

如果 Objective 明确声称：

- 熟练；
- 稳定；
- 长期保持；
- 能在多种场景持续完成；

才自然要求：

- 多次表现；
- 不同场景；
- 必要的时间跨度。

V1 应少创建“熟练”型 Objective，避免被迫建设复杂熟练度评分系统。

---

## 15. 延迟验证主要属于 Review System，不是首次掌握统一门槛

刚学完后答对，可以形成有效当前证据，但对长期保持证明较弱。

Study Agent 不要求所有 Objective 都必须隔几天再测试，才能第一次标记“已掌握”。

正确关系：

```text
首次证据满足能力验证规则
↓
已掌握
↓
时间过去 / 需要重新确认
↓
Review System
↓
review_due
↓
新的真实表现
↓
重新形成近期 Evidence
```

历史 Evidence 不因时间删除。

---

## 16. “需要复习”不等于“从未掌握”

状态应允许：

```text
学习中
↓
待验证
↓
已掌握
↓
需要复习
↓
重新验证
↓
已掌握
```

“需要复习”表示：

> 历史上已经有足够证据证明会过，但当前值得重新激活或确认。

不能通过删除旧 Evidence 把历史改写成“用户从来不会”。

如果复习中出现新的强冲突证据，应新增 conflicting Evidence，再由当前证据集合重新裁决。

---

## 17. 掌握不是成功次数，而是当前证据集合满足规则

锁定公式化语义：

```text
当前有效 Evidence
        ↓
是否覆盖 Objective 要求的能力维度？
        ↓
是否缺少关键 Evidence？
        ↓
是否存在近期强冲突？
        ↓
Learning Task Domain 裁决状态
```

因此：

> **Mastery 是“当前证据集合满足能力验证规则”的结果，不是累计成功次数达到阈值。**

---

## 18. “已掌握”的最终 Owner 是 Learning Task Domain

系统必须避免多个模块都能写 mastery。

锁定：

> **Learning Evidence System 负责证明；Learning Task Domain 负责裁决。**

Learning Evidence System 输出：

- supporting Evidence；
- conflicting Evidence；
- missing Evidence；
- Evidence Type；
- 帮助程度；
- 新场景程度；
- 时间相关性；
- 可追溯来源。

它不直接写：

```text
mastered = true
```

Learning Task Domain 同时读取：

```text
学习证据视图
+
Objective 的能力验证规则
```

然后拥有 Objective 当前能力状态的最终写权限。

---

## 19. 为什么 Evidence System 不能直接宣布“已掌握”

同一组 Evidence 对不同目标可能得出不同结论。

例如现有证据：

```text
✓ 能解释 self-invocation
✓ 能判断标准代码案例
✓ 能在一个新案例中发现 proxy bypass
```

对于 Objective：

```text
能解释 self-invocation 为什么导致事务增强失效
```

可能已经足够。

但对于更大的 Learning Task：

```text
能独立排查生产环境常见 Spring 事务失效问题
```

显然还可能缺少传播机制、异常回滚、多 Bean 调用等能力。

所以“是否掌握”必须相对于 Objective / Task 的完成标准裁决。

---

## 20. 用户声明与系统验证状态必须分离

用户说：

```text
“这个我会了。”
```

系统应记录的是：

```text
用户自述：claims_known
```

而不是直接：

```text
系统验证：mastered
```

概念上至少区分：

```text
User Claim
- claims_known
- claims_uncertain
- claims_not_known

System Mastery State
- learning
- pending_verification
- mastered
- needs_review
```

字段名可调整，但语义必须分离。

用户声明可以立即影响：

- 路线；
- 是否继续讲；
- 是否主动验证；
- 是否跳过当前 Objective。

但不能篡改历史 Evidence。

---

## 21. 用户说“我不会”时，系统不能拿旧证据和用户争

如果系统此前判定“已掌握”，用户明确说：

```text
“其实我没懂。”
```

系统必须立即尊重这一声明：

- 恢复教学；
- 允许重新学习；
- 重新验证；
- 不把目标继续当作无需干预。

历史 Evidence 仍保留。

这不是用户篡改历史，而是新增高价值当前信号。

硬原则：

> **用户不能伪造系统验证，但系统也不能用旧验证否定用户当前真实学习感受。**

---

## 22. LLM 与角色无权直接写 mastery

LLM / Teaching Agent 可以：

- 教学；
- 提问；
- Assessment；
- 产生 Evidence candidate；
- 生成 supporting / conflicting Evidence 的语义判断。

不能：

```text
mastered = true
```

角色说：

```text
“你这次真的想明白了。”
```

属于角色表达，不是系统裁决。

Group Orchestrator、角色聊天、Memory extractor 都不得通过鼓励语或推测更新 mastery。

---

## 23. Objective 状态与 Learning Task 状态分离

Learning Task 可能包含多个 required Objective。

例如：

```text
O1 解释代理机制            已掌握
O2 判断 self-invocation   已掌握
O3 判断传播机制            待验证
O4 新代码独立排错          学习中
```

此时整个 Task 还不能判定目标已达成。

推荐产品语言：

- Objective：`已掌握`
- Learning Task：`目标已达成`

避免把学习产品做成 Jira 的“任务 Done”。

---

## 24. 状态变化必须可解释

Objective 从：

```text
已掌握
```

变化为：

```text
需要复习
```

必须能够回溯原因，例如：

```text
from = mastered
to = needs_review
reason = new_conflicting_transfer_evidence
trigger = evidence_382
```

或：

```text
reason = review_window_reached
```

时间到期与真实失败证据必须区分，因为后续教学策略不同。

---

## 25. Review System 只有调度权，没有“宣布忘记”的权力

Review System 可以判断：

```text
review_due
```

它不能直接写：

```text
mastery = false
```

复习后产生新的真实 Evidence，再由 Learning Task Domain 根据能力验证规则重新裁决。

因此：

> **“到了复习时间”不是“用户已经不会了”。**

---

## 26. Event Ledger 不能反向成为掌握状态 Owner

因果方向必须是：

```text
Evidence / Review / Task state change
↓
Domain Authority
↓
Trusted Event
↓
Event Ledger
```

而不是：

```text
Event
↓
直接修改 mastery
```

Event 是状态变化与未来行动的可追溯投影，不是学习真值本身。

---

## 27. 各系统写权限

| 系统 | 可以做什么 | 不可以做什么 |
|---|---|---|
| Learning Evidence System | 记录、评估、聚合学习证据，提供学习证据视图 | 直接宣布整个 Task 目标已达成 |
| Learning Task Domain | 根据能力验证规则裁决 Objective / Task 状态 | 自己重新解释完整聊天生成第二套 Evidence |
| LLM / Teaching Agent | 教学、Assessment、提出 Evidence candidate | 直接写 `mastered` |
| 用户 | 改路线、跳过、声明会/不会、要求重新学习 | 篡改系统历史 Evidence |
| Route System | 规划下一步 | 修改 mastery 真值 |
| Review System | 判断复习时机 | 宣布用户已经忘记 |
| Group Orchestrator | 呈现、讨论、鼓励 | 修改用户能力事实 |
| Event Ledger | 保存可行动事件 | 成为学习状态真值 Owner |

核心架构原则：

> **一个事实，一个 Owner。**

---

## 28. 当前明确禁止的实现

1. 不允许 `做对 N 次 = mastered` 成为统一规则。
2. 不允许二选一猜中一次直接形成强 mastery。
3. 不允许 Agent 给出关键答案后，把用户复述记录成独立能力。
4. 不允许把正常文档、搜索、IDE、RAG 资料辅助一律判成“不独立”。
5. 不允许为了 Evidence 纯度拒绝用户明确要求的帮助。
6. 不允许真实项目由 Agent 完成后，把项目成功记成用户能力证据。
7. 不允许所有 Objective 强制延迟复测。
8. 不允许时间过去后删除历史 Evidence。
9. 不允许 `needs_review` 与 `never_mastered` 混为一谈。
10. 不允许 Learning Evidence System、LLM、Group、Route、Review 同时拥有 mastery 写权限。
11. 不允许用户一句“我会了”直接伪造系统验证状态。
12. 不允许系统因历史 Evidence 与用户争论“你其实会”。
13. 不允许角色鼓励语进入 mastery 真值链。
14. 不允许 Event Ledger 反向成为学习状态 Owner。

## 29. V1 验收原则

### 29.1 能力强度与验证强度一致

`知道 / 理解 / 应用 / 独立使用` 至少能映射到不同的最低 Evidence 要求。

### 29.2 独立使用必须有新场景证据

任何声称“独立排查 / 设计 / 解决”的 Objective，都能回溯到至少一次独立的新场景应用表现。

### 29.3 提示程度可追溯

强 Evidence 能说明用户成功前 Agent 是否给过关键提示；结构化教学动作优先提供该信息。

### 29.4 Agent 自己完成不算用户掌握

用户没有产生真实表现时，不生成用户能力 Evidence。

### 29.5 不靠次数阈值

Mastery 能解释为 Evidence 组合满足能力验证规则，而不是 `correct_count` 达到阈值。

### 29.6 历史掌握与当前复习状态可同时成立

进入 `needs_review` 时，历史 Evidence 与曾经满足 mastery 的记录仍然存在。

### 29.7 用户自述与系统验证可同时存在且不互相覆盖

用户可以声明“会 / 不会”，路线立即响应，但系统验证状态保留独立来源。

### 29.8 Mastery 单一 Owner

只有 Learning Task Domain 能根据能力验证规则与学习证据视图修改 Objective / Task 的正式能力状态。
