# Study Agent 离线群聊事件模型设计

> 文档类型：产品设计规范 / GrillMe 已锁定专项设计  
> 状态：locked  
> 日期：2026-08-08  
> 上位约束：`superpowers/specs/2026-08-07-product-design-direction-design.md`  
> 适用范围：Learning Event、Relationship Event、群聊离线行为、Group Orchestrator、未读语义、学习状态与群聊边界

---

## 1. 决策摘要

Study Agent 的群聊采用：

> **事件驱动的延迟群聊（event-driven deferred group chat）。**

核心原则：

> **离线时不让角色无目的聊天；离线时只积累真实发生的事件。**

群聊不是一个独立运行、为了制造活跃度而无限生成消息的世界模拟器。它是学习系统的社会化呈现层：真实学习状态与关系状态先变化，只有当某个变化值得被角色拿出来讨论时，才由 Group Orchestrator 将事件物化为群聊消息。

---

## 2. Activity 与 Message 必须分离

硬边界：

> **Activity ≠ Message。**

必须区分：

```text
Learning Event / Relationship Event
= 系统中真实发生的状态变化或可追溯事件

Group Message
= 已经真正生成并持久化、用户可以阅读的群聊消息
```

不能把“系统检测到一个值得讨论的事件”直接伪装成“已经存在若干条未读消息”。

正确链路：

```text
真实事件发生
    ↓
Event Ledger
    ↓ 可选
Group Orchestrator
判断：这件事值得拿到群里说吗？
    ↓
否 ──→ 安静，不生成消息
是 ──→ 分配本轮认知职责
         ↓
      生成角色互动
         ↓
      持久化 Group Message
         ↓
      此时才产生真实 unread
```

事件可以存在，但不一定产生消息。

Agent 必须拥有“什么都不说”的能力。

---

## 3. Learning Event Ledger

离线期间默认只记录或补算真实学习事件，不持续调用多个角色进行对话。

建议建立 `Learning Event Ledger` 概念，记录可追溯的学习状态变化。

示例：

```text
2026-08-08 09:00
review_due
task=transaction-propagation

2026-08-08 11:21
source_updated
repo=study-agent
commit=abc123

2026-08-08 14:30
task_signal
task=jwt-refresh-token
reason=unfinished_question
```

允许的典型 Learning Event 包括：

- 某 Learning Task 进入适合复习的时间窗口；
- 用户设置的重要考试、面试、课程或截止日期接近；
- 用户订阅的源码仓库、CI、资料或外部学习来源发生真实变化；
- 新资料完成索引；
- 上一次 Learning Session 留下未解决问题；
- 路线重算发现真正会阻碍当前目标的前置缺口；
- 学习证据发生状态变化；
- 某 Learning Task 达到待验证条件；
- 用户明确创建的学习计划触发。

禁止为了给群聊找话题而虚构 Learning Event。

---

## 4. Relationship Event

仅依赖 Learning Event 会让角色退化成机械通知机器人，因此允许第二类触发：

> **Relationship Event。**

它服务于角色关系连续性，而不是直接教学。

允许的典型 Relationship Event 包括：

- 用户完成一个长期或困难目标；
- 用户连续推进一个长期项目；
- 用户在真实交互中表现出明显疲惫、挫败或兴奋，并且该状态值得后续延续；
- 用户长时间没有进入某条自己明确重视的长期路线；
- 角色关系状态基于真实用户交互发生有意义变化；
- 用户明确要求角色以后关注某件事。

示例：

```text
三月七：你昨天总算把那个问题搞明白了，老实说我还挺替你高兴的。
```

这种内容不需要强行承担知识教学作用，它的产品价值是：

> **维持长期学习伙伴关系的连续性。**

但 Relationship Event 仍必须有真实依据，不能为了“角色显得活着”随机创造。

---

## 5. 群聊是学习系统的社会化呈现层

新的数据关系应明确为：

```text
Learning Task
     │
     ├── 学习事件
     ├── 掌握证据
     ├── 复习状态
     ├── 路线变化
     └── 真实外部变化
             │
             ↓
        Event Ledger
             │
             ↓
      Group Orchestrator
             │
      值得讨论吗？
       ↙        ↘
     否          是
     │           │
   安静      动态认知分工
                 ↓
             Group Message
```

因此群聊不再维护一套与 Learning Task 平行、竞争甚至冲突的“学习真相”。

Learning Task 仍然是：

- 学习目标 owner；
- 掌握状态 owner；
- 学习证据 owner；
- 路线状态 owner。

群聊负责：

- 把值得讨论的真实事件社会化呈现；
- 提供多视角解释；
- 维持角色关系连续性；
- 提出建议、问题、例子、资源和路线建议；
- 让学习系统拥有“伙伴在一起”的体验。

---

## 6. 群聊不能产生自反馈学习事实

已有上位原则：

> **NPC 对话可以产生建议，不能产生用户学习证据。**

本专项规范进一步扩展：

> **NPC 对话也不能凭自身推测修改用户能力事实。**

禁止链路：

```text
Agent A 猜测用户不会 X
↓
Agent B 接受这个猜测
↓
群聊摘要把它写成事实
↓
学习路线据此认为用户不会 X
↓
后续 Agent 再用该路线强化原猜测
```

任何用户能力判断必须回到可追溯来源，例如：

- 用户真实回答；
- 用户真实练习结果；
- 用户真实代码或作品；
- 用户明确陈述；
- 可验证的 Learning Evidence。

群聊内部生成的推测只能作为低权限建议，不能升级为用户事实。

---

## 7. Event Origin 必须可追溯

为避免真实经历、系统事件、AI 生成内容和角色扮演混在一起，后续数据模型至少应保留事件来源语义。

建议 origin 类型：

```text
user
system_event
external_source
agent_generated
roleplay
```

不同 origin 必须有不同权限。

尤其：

- `user` 可成为用户事实或学习证据候选；
- `system_event` 可触发学习流程或提醒；
- `external_source` 必须保留来源与时间；
- `agent_generated` 不能自动成为用户事实；
- `roleplay` 不能进入学习证据体系。

是否采用以上精确字段名属于实现层决定，但来源隔离是不变量。

---

## 8. 未读语义

“未读”只能表示已经存在的、持久化的 Group Message 尚未被用户阅读。

严格区分三种 UI 状态：

### 8.1 已存在消息

```text
3 条未读
```

只有数据库中已经真正存在 3 条未读 Group Message 时才能显示。

### 8.2 只有事件，尚未物化消息

推荐：

```text
有新动态
```

或：

```text
有 2 件事值得关注
```

不能显示“7 条未读”。

### 8.3 Agent 判断值得进入群聊讨论

可以使用：

```text
大家有件事想和你聊
```

这是 suggestion/activity，不是 unread。

硬边界：

> **没有真实 Message，就不能伪装成未读 Message。**

---

## 9. 离线期间默认行为

默认模式：

```text
用户离开
  ↓
不持续生成 NPC 对话
  ↓
真实事件继续发生 / 下次启动时补算
  ↓
写入 Event Ledger
  ↓
不为无价值事件生成消息
```

因此：

- 无有意义事件时，离线模型调用可以为 0；
- 离线越久不应自然导致几十、几百条 NPC 消息；
- 群聊不会因为用户几天没打开 App 自动制造 backlog；
- 产品不应制造“我欠群里几十条消息没看”的未读焦虑。

这使后台成本更接近：

```text
成本 ≈ 有意义事件数量
```

而不是：

```text
成本 ≈ 离线时间 × 角色数 × 活跃频率
```

---

## 10. 本地优先架构兼容

事件驱动模型必须允许 Study Agent 并非 24×7 在线。

如果应用关闭，下一次启动可以根据：

- `last_seen_at`；
- Learning Task 状态；
- review schedule；
- deadline；
- 可查询外部来源状态；

补算期间真实发生的事件。

例如：

```text
last_seen_at = Aug 7
now          = Aug 10

补算：
- review_due
- deadline_near
- repository_changed
```

因此 V1 不要求为了群聊而引入永久在线 daemon / cloud service。

未来如果增加在线后台服务，它只是增强 Event Ledger 的实时性，不改变本规范的数据语义。

---

## 11. Group Orchestrator 的职责边界

Group Orchestrator 不应该对每一个 Event 都生成对话。

它至少应判断：

- 该事件是否对用户当前学习有价值；
- 是否已经以其他方式表达过；
- 是否适合现在进入群聊；
- 是否只是低价值噪声；
- 是否值得多个角色参与；
- 哪些认知职责能够产生真正不同的视角；
- 是否应该保持安静。

重要原则：

> **生成消息不是 Orchestrator 的默认成功状态；正确地保持安静同样是成功。**

如果决定讨论，再动态分配角色认知职责，避免多个角色重复同一答案。

---

## 12. 首页与群聊入口

当前锁定方向：

首页只展示 Activity 层，不为了首页展示而提前制造完整群聊对白。

首页可展示：

```text
学习伙伴群
有新动态
```

或：

```text
学习伙伴群
有 2 件事大家可能想和你聊
```

默认不展示虚假的“X 条未读”。

用户真正进入群聊后，再将值得讨论的 Event 物化为 Group Message，是当前推荐行为。

这既保持首页极简，也避免群聊反过来抢占核心 Learning Task 流程。

---

## 13. 当前明确禁止的实现

1. 不允许定时让四个角色无目的无限互聊。
2. 不允许为了 DAU、活跃度或“生命感”随机制造群聊内容。
3. 不允许先显示“X 条未读”，用户点击后才临时生成这 X 条消息。
4. 不允许 NPC 推测直接写入用户能力事实。
5. 不允许 NPC 对话直接产生用户掌握证据。
6. 不允许 roleplay 内容混入 Learning Evidence。
7. 不允许事件存在就必然生成群聊消息。
8. 不允许离线时间越长，未读量自然无限增长。
9. 不要求 V1 为群聊引入 24×7 云后台。
10. 不允许群聊维护一套与 Learning Task 冲突的学习状态。

---

## 14. 验收原则

后续实现本功能时至少应验证：

### 14.1 真实性

- 只有真实存在的 Message 才计 unread；
- Event 有可追溯 origin；
- NPC 推测不会写入用户掌握状态。

### 14.2 克制性

- 无事件时不会产生后台模型调用；
- 低价值 Event 可以被静默过滤；
- 多个相近 Event 可以聚合处理；
- 用户离线多日不会产生无限消息 backlog。

### 14.3 学习一致性

- 群聊内容可以引用 Learning Task；
- 群聊产生的学习结论只能成为建议或待验证候选；
- 用户真实参与后产生的新证据，才可进入 Learning Evidence 流程。

### 14.4 角色价值

- 同一个 Event 的多角色讨论必须体现不同认知职责；
- 不允许四个角色简单换措辞重复同一个答案；
- Relationship Event 可以维持人格连续性，但不能虚构用户经历。

### 14.5 本地恢复

- 应用关闭后重新启动，可以补算必要 Event；
- 补算不得重复生成同一事件；
- 补算失败不得破坏现有 Learning Task 或群聊历史。

---

## 15. 一句话原则

> **群聊离线时继续生活在学习系统里，但不继续制造对话；真实事件先发生，角色语言只在值得呈现时产生。**
