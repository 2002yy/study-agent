# 研究执行方式 A/B 计划：RQCE vs 模型主导（2026-11-27）

状态：**已授权并执行**（1 题 × 2 路径，¥2 上限，图片关闭）。
结果见 RESEARCH_MODE_AB_RESULTS_20261127.md；本文保留原始协议，供复现与对照。

## 1. 要回答的问题

在相同问题、相同模型、相同搜索/读取工具、相同费用上限下，**让模型主导研究（B）是否比程序主导的 RQCE（A）产出更好的最终答案**？

本轮不验证"多接一个读取器"或"多一个平台"的价值，只验证研究执行方式。

## 2. 对照设计

| 控制项 | 设置 |
| --- | --- |
| 问题 | 同一条 Godot + Jolt 问题（见 §3） |
| 模型 | 同一 `flash` 模型与 provider（`.env` 不变） |
| 工具链 | 同一搜索优先级、读取器、SSRF/平台范围、账本、证据准入 |
| 入口 | `ChatService.start_turn` + `generate`，与产品链路一致 |
| 时间窗 | 两臂都是 Deep 档：研究 600 秒 + 答案 60 秒 |
| 读取预算 | 页面 15 / 文档 30 / PDF 60 / 媒体 330 秒；并行读取上限 3 |
| 并行搜索 | 关闭（`WEB_AUTONOMOUS_PARALLEL_SEARCH` 默认 off） |
| 运行隔离 | 每臂独立进程、独立 runtime DB、独立 media cache |
| 账本 | 两臂共享一个实验账本与硬上限 |
| 图片 | 关闭：无附件、无 vision 调用 |

两条路径由同一入口的开关选择：

- **A（RQCE）**：`WEB_AUTONOMOUS_RESEARCH` / `WEB_AUTONOMOUS_DEEP` 都不设置。问题以 `请深度研究：` 开头 → `_resolve_deep_research`。
- **B（自主）**：`WEB_AUTONOMOUS_RESEARCH=1`、`WEB_AUTONOMOUS_DEEP=1`。同一前缀 → `_resolve_autonomous(deep=True)`。

路径选择是确定性的；运行记录里用 `web_tools`、research run 行与 `stop_reason` 复核实际走的是哪条。

## 3. 问题

沿用 E0 已用过的同题，便于对照历史读取结果：

```text
请深度研究：在 Godot 4.x 中使用 Jolt 物理做建筑/掩体的可破坏结构，
哪些技术限制是真实存在的？请给出可执行的做法与失效边界。
```

| 项 | 值 |

**计量边界（必须如实记录）**：

- 账本硬上限覆盖的是**模型调用预留**；DeepSeek Search / Fetch 属于 provider 侧计费，不经过本账本，只受请求次数上限约束。其单价未在本机核实，只能记录调用次数，不能宣称"总费用一定 ≤ ¥2"。
- 参考 E0 同一 Deep 档实测：每臂约 ¥0.197–0.207。两臂预期 ¥0.4–0.5，¥2 上限有约 4 倍余量。
- 账本只增不减；达到上限时后续调用被拒绝，不做自动重试。

## 5. 运行顺序

1. **先跑 B**（自主路径）：本轮的核心未知是它能否在真实模型下完成研究。
2. B 产出可用答案后，再跑 A（RQCE）。
3. B 若在框架层失败（异常、无 run、无法生成答案），停止并报告，不自动重跑；是否仍跑 A 由用户决定。

理由：B 是新增路径，失败概率更高；先跑 B 可以把预算花在真正的未知上。

## 6. 每臂要记录的证据

结果目录：`.../rab-results/<arm>/`

- `result.json`
  - `status`、`route`、`task_contract`
  - `answer`（全文）、`answer_chars`
  - `web_tools`：`enabled` / `error` / `calls` / `recovery` / `semantics`
  - `research_runs`：每条 run 的 `stage`、`status`、`stop_reason`、`source_block` 长度、`selected_sources` 条数、`provider_status`
  - `elapsed_seconds`（研究 + 答案合计）
  - `spend_before_micros` / `spend_after_micros`
- `runtime.db`：完整工具轨迹、读取结果、rejected/exploration 记录
- 另存一份 `answer.md`，便于盲评

运行后离线计算（不再调用模型）：

- 模型调用次数、工具调用次数、搜索/读取次数、读取成功/失败数
- 来源域名分布、官方文档/源码是否进入证据
- 两臂的 `source_block` 组成：来源数、字符数、每来源被保留的比例
- 中文问题词与英文页面的字面命中率（观察项 2）

## 7. 评分

先建参考事实清单，再读答案，避免被答案带偏。参考事实只取官方文档、发布说明、源码与可核查的一手资料，每条带 URL。

| 维度 | 权重 | 判定要点 |
| --- | ---: | --- |
| 事实准确性 | 30% | 参考事实中正确/错误/无依据的比例；版本号、API 名、限制条件必须准确 |
| 核心问题覆盖率 | 25% | 问题要求的"限制、可执行做法、失效边界"三部分是否都有实质回答 |
| 有价值的新发现 | 15% | 是否给出参考清单之外的、可核查的机制或实践 |
| 反例与局限性分析 | 15% | 是否说明何时不适用、常见失败模式、版本差异 |
| 证据质量与可追溯性 | 15% | 引用是否指向真实读过的来源；结论与来源是否对得上 |

评分方式：

- 两臂答案去掉标识后随机编号，先按维度打 0–5 分，再乘权重；
- 记录每条参考事实的"命中/错误/缺失"；
- 事实错误一票记录，不用总分掩盖；
- 运行时间、调用次数、费用单列，不进入质量分。

## 8. 本轮要观察、但不修改的三点

1. **60,000 字符是触发阈值，不是硬上限。** 最近两轮不压缩时仍可能超出。本版没有把压缩统计持久化到 trace，因此只能做近似观察：用持久化的工具调用数与结果字符数估算各轮规模，并检查答案是否漏掉后期读到的内容。
2. **相关段落依赖字面词匹配。** 中文问题 + 英文文档可能命中不足。离线统计被准入英文页面的问题词命中数；命中为 0 的页面单独列出。
3. **压缩后的研究记忆只保留旧结果前 700 字符。** 检查 B 的答案是否覆盖"后期读取才出现的发现/反例"；若出现遗漏，记为压缩策略的实测代价，不在本轮修。

三点都只记录，不因观察结果临时加机制。

## 9. 停止条件

- 账本拒绝调用 → 停止该臂，保留已有结果，记录 `spend_cap_refused`。
- provider/API 失败 → 不重试，记录错误与已收集证据。
- 没有可用来源 → 记录 candidate-only，不补造答案。
- B 框架异常 → 停止，报告，不自动重跑。
- 任何一步发现凭据、范围或账本配置异常 → 立即停止，不"先跑再说"。
