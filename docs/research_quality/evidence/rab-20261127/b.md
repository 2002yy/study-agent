## 先把问题切成三层，Jolt 只负责其中一层

“可破坏建筑”这个说法里其实混了三件互相独立的事，它们的难点完全不同：

1. **几何切分**：一块墙要碎成哪些块、每块的形状是什么。这是**离线问题**（Blender / 工具链），和物理引擎无关。
2. **碰撞与求解**：碎片之间怎么堆、怎么撞、怎么休眠。**这是 Jolt 的职责，也是它真正强的地方。**
3. **结构连接**：墙没被打穿之前，为什么整块墙不会自己塌。这是**约束问题**，而 Godot 暴露的约束 API 很薄。

很多“Jolt 做不了可破坏结构”的说法，实际卡在第 1 层或第 3 层，Jolt 本身没有问题。分清这一点，后面的限制才好判断哪些必须接受。

## 真实存在的限制

### A. 引擎级硬边界（换物理引擎也绕不过）

**A1. 动态碰撞体不能是凹面体。** Godot 的 `ConcavePolygonShape3D`（三角网格）只能用在静态或不动的东西上。碎片一旦要飞、要翻滚，就必须是凸包或凸包组合。这不是 Jolt 的偏好，是所有实时引擎的共同前提：GJK/EPA 这类算法只对凸体成立。

**A2. 没有运行时破碎 API。** Godot 4 没有“给一个 mesh，还我一堆带碰撞体的碎片”的能力。CSG 节点能做布尔差集，但 CSG 生成碰撞体的开销是导入级的，不适合在战斗帧里调用。**结论：切分必须在离线完成**（Blender Cell Fracture、Voronoi 预烘焙，或自己写工具烘焙每个 chunk 的凸包）。这条是设计前提，不是可优化项。

**A3. 凹分解（convex decomposition）不能在运行时做。** 一个带门窗洞口的墙，凹分解出来可能是 8~20 个凸包。V-HACD 这类算法是几十到几百毫秒级的，放在破坏瞬间就是必然卡顿。**边界：只在导入期做，运行时只查表。**

### B. Jolt 与 Godot 结合部的限制（相对 Godot Physics 的差异，需实测确认）

**B1. 关节没有“断裂阈值”。** Godot 暴露 `PinJoint3D` / `HingeJoint3D` / `Generic6DOFJoint3D`，但**没有读取约束反作用力的 API**，也没有 break force。所以“受力超过 X 就断”无法直接实现。这是本项目最真实的一条限制。

绕过方式不是调参数，而是**换模型**：不要用关节去连接碎片，而是让整栋建筑在没有被打中时是**一个整体静态碰撞体**，被打中时才把那一块“升级”成独立刚体。这样根本不需要关节，也就不需要断裂判定。

**B2. 接触冲量拿不到可靠数值。** `RigidBody3D.contact_monitor` + `max_contacts_reported` 在 Jolt 后端下的完整度需要在你版本上验证；即便可用，逐接触点做伤害计算也很昂贵，而且接触点在持续碰撞中不稳定。**建议：伤害判定走射线或形状投射（`PhysicsDirectSpaceState3D`），不要走接触监听。**

**B3. 凹面体的“内部边缘伪碰撞”（ghost collision）。** 弹丸沿墙面滑过时可能被三角形内部边“绊”一下。Jolt 有内部边缘消除的机制，效果通常优于 Godot Physics，但**薄壁、双层三角面、非流形网格仍会失效**。这是网格质量问题，不是引擎参数问题。
*需实测：你的墙体网格是否单面、是否有重叠面。*

**B4. 休眠与唤醒是“岛级”的。** Jolt 的休眠很激进——这对性能是好事。但反过来说：**唤醒一块碎片，可能唤醒与它接触的整个连通体**。一栋 300 块的楼，打掉底层一块砖，可能让整个结构一起被唤醒求解，出现单帧物理耗时尖峰。这条限制在纸面上不明显，实际项目里最扎人。

**B5. SoftBody3D 不支持**（据我所知 Jolt 后端未实现）。如果你的“掩体”里有沙袋、布料、软性挡板，这些得走 Godot Physics 或换成刚体近似。
*需实测：`SoftBody3D` 在你的 Jolt 版本下是否直接报错还是静默不动。*

**B6. 世界尺度敏感。** Jolt 的参数（睡眠速度阈值、穿透容差、摩擦）按“1 单位 ≈ 1 米”标定。若你的项目按 1 单位 = 1 厘米建模，碎片尺寸 5 单位、重力 9.8，所有阈值都错位，表现为碎片抖动、莫名穿透、永不入睡。**这条被严重低估，实际是“Jolt 不好用”报告的第一大来源。**

**B7. CCD 有代价也有盲区。** 快速弹丸打薄墙会穿透。连续碰撞检测能用，但只处理线性扫描，**高速旋转的长条碎片仍会穿透**，而且 CCD 开了之后开销不小。**边界：薄于约 5 cm 的墙 + 速度超过 100 m/s 的弹丸，必须靠射线预判命中，而不是靠物理碰撞。**

**B8. 确定性不保证跨平台。** 多线程求解 + 浮点差异，客户端各自跑物理会分歧。**边界：联机模式下，破坏结果必须由“伤害事件 + 血量”决定，物理只做表现。**

### C. 项目级工程边界（不是引擎的限制，但你一定会撞上）

- **节点开销比求解开销更致命。** Jolt 能算几千个刚体，但 Godot 每个碎片是一个 `RigidBody3D` + `CollisionShape3D` + `MeshInstance3D`，节点树、变换同步、渲染批次都会先撑不住。**碎片渲染应该走 `MultiMeshInstance3D`，碰撞体数量用对象池硬性封顶。**
- **活跃碎片上限是硬预算。** 桌面 200~400 个活跃刚体、移动端 50~100 个、Web 更少。这是我的估计量级，不是实测数据，请在目标设备上量。
- **物理步进发生在物理帧上**，卡顿表现为“帧时间尖峰”而不是平均帧率下降。所以要给破坏加**每帧生成配额**（例如每帧最多激活 8 个碎片，其余排队）。

## 可执行做法：三层管线

### 层 1：离线切分（一次性，导入期）

1. Blender 里对每面墙/掩体做 Cell Fracture（或用 Voronoi 脚本），每块单独 export 为 mesh。
2. 每块生成**凸包碰撞体**。凹形块在导入设置里做凸分解，烘焙成 `ConvexPolygonShape3D` 数组。
3. 把每块的位置、凸包、子树索引、HP 写进一份资源（`Resource` 或 JSON），运行时只读。

### 层 2：运行时结构——推荐“冻结碎片”模型

不要做“静态墙 + 破坏时生成碎片”两套东西。**从第一帧起，整栋建筑就是一堆冻结的刚体**，未破坏时它们不参与求解。

```gdscript
# 每个碎片是一个 RigidBody3D，freeze 模式设为 STATIC
# 这样它等价于静态碰撞体，参与射线检测，但不进求解器
func _ready() -> void:
    freeze_mode = RigidBody3D.FREEZE_MODE_STATIC
    freeze = true
    can_sleep = true

# 被破坏时解冻
func shatter(impulse: Vector3, at: Vector3) -> void:
    freeze = false
    # 关键：解冻瞬间给一个微小分离量，否则互相穿插会爆开
    apply_impulse(impulse, at - global_position)
    # 若开了物理插值，必须重置，否则碎片会从原位"滑"过来
    reset_physics_interpolation()
```

优点：没有运行时节点增删，没有 broadphase 重建，碎裂是“解冻 + 施加冲量”两行。缺点：碎片永远是节点，节点数 = 碎片数，一栋楼几百块就到顶了。

**超过几百块的场景**改用“单体 compound + 对象池”：
- 建筑是一个 `StaticBody3D`，用 `shape_owner_create()` / `shape_owner_add_shape()` 把每个 chunk 的凸包挂上去；
- 被破坏时 `shape_owner_set_disabled(owner_id, true)` 让那块失去碰撞；
- 同时从池里取一个 `RigidBody3D` 把视觉碎片放出去。

（`body_shape_entered` 回调会带 `body_shape_index`，可以映射回 chunk 索引——**但这个映射在 Jolt 后端下是否稳定，需要你实测**。）

### 层 3：伤害判定——不走接触监听

```gdscript
# 弹丸用射线或形状投射判定命中，自己算伤害
func fire(from: Vector3, dir: Vector3, damage: float) -> void:
    var q := PhysicsRayQueryParameters3D.create(from, from + dir * 200.0)
    var hit := get_world_3d().direct_space_state.intersect_ray(q)
    if hit.is_empty():
        return
    var target := hit.collider as Node
    if target.has_method("take_hit"):
        # 命中点 + 法线 + 冲量方向，由建筑自己决定碎哪块
        target.take_hit(hit.position, dir, damage)
```

建筑侧维护 `chunk_hp` 数组，`take_hit` 里找最近 chunk、扣血、血量为 0 就切到层 2 的解冻流程。**这样破坏逻辑完全可控、可联机同步、可回放，而且不依赖任何 Jolt 内部数值。**

### 层 4：清场

碎片入睡后（`sleeping` 变 true）等 2~3 秒，转成 `FREEZE_MODE_STATIC` 或直接并入一个“瓦砾堆”的静态网格，把刚体名额还给池子。不回收的话，一场战斗打完，物理世界就废了。

## 失效边界：什么时候这套会崩

| 触发条件 | 症状 | 应对 |
|---|---|---|
| 碎片尺寸 < 3~5 cm | 抖动、互相穿插、永不入睡 | 世界尺度按米；碎片最小尺寸定死；小碎屑只用视觉粒子不做碰撞 |
| 单次破坏激活 > 30 个碎片 | 物理帧尖峰（不是平均帧率下降） | 每帧激活配额 + 排队 |
| 底层承重块被毁 | 整岛唤醒，单帧求解爆炸 | 建筑分层：承重层用静态体，只在视觉上“塌”，不做真实堆叠求解 |
| 薄墙（< 5 cm）+ 高速弹丸 | 穿透 | 射线预判命中，物理碰撞只做兜底 |
| 联机 + 客户端各自模拟 | 建筑状态分歧 | 破坏走事件同步，客户端物理只做表现，定期以服务端状态校正 |
| 网格非流形 / 双面重叠 | 弹丸被内部边“绊”或穿墙 | 导入期做网格清理和单面化 |
| 一栋楼 > 500 块碎片节点 | 节点树与渲染先崩，不是物理 | 换 compound + MultiMesh + 对象池 |
| 目标设备是 Web / 低端移动 | Jolt 多线程与内存受限 | 降碎片预算，关物理插值，保留静态 compound 方案 |

## 请在你自己的版本上核实这 5 件事

我给的是结构判断，具体数值和 API 完整度会随 Godot 4.x 小版本变化。打开编辑器后确认：

1. `Project Settings` 里搜 `jolt`，看有哪些分组（求解步数、睡眠阈值、碰撞设置在哪）；
2. `SoftBody3D` 在 Jolt 后端下的行为（报错 / 静默不动 / 正常）；
3. `RigidBody3D.contact_monitor` 是否能正常触发；
4. `body_shape_entered` 的 `body_shape_index` 在 compound 静态体上是否指向你添加的 shape；
5. 高速刚体的 `continuous_cd` 在你的版本下是否真的生效（做个 200 m/s 打 2 cm 薄板的极限测试）。

**一句话收束**：Jolt 在这些场景里真正的短板是关节和冲量回读；真正拖垮项目的是运行时破碎和节点数量；真正会让人误判“Jolt 不行”的是世界尺度和休眠唤醒尖峰。把破坏做成“离线切分 + 冻结碎片 + 射线性伤害判定”，Jolt 完全够用，而且比 Godot Physics 稳。
