# 分段覆盖评估（零成本）

> 数据：`docs/research_quality/answer_ab` 的 20 轮归档答案；
> 费用：0；重现：`PYTHONPATH=. python tools/segmentation_coverage.py`；
> 本评估**不改任何生产预算**，只测量两个独立限制的影响。

## 1. 现状：两个独立限制

- 当前 `_MAX_SEGMENTS = 16`、`_MAX_SEGMENT_CHARS = 1200`；任一触发即整份答案被拒；
- 当前可进入绑定：**7 / 20**；
- 其中因**段数**被挡：13；因**单段过长**被挡：0。

这条区分很重要：如果被挡的答案里有单段超过 1200 字符，单纯提高段数上限也救不回来。

## 4. 结构感知分段的探针（不修改生产）

把 Markdown 标题视为结构（不计为事实）、表格行与列表项各算一个事实单元、代码块整体算一个单元、其余按生产分段正则切句。

| 指标 | 值 |
| --- | ---: |
| 现有规则的总分段数 | 730 |
| 结构感知探针的总单元数 | 433 |
| 减少的单元数 | 297 |
| 结构规则下能进 16 段的答案 | 9 / 20 |
| 数字丢失（标题以外，应恒为 0） | **0** |
| 仅出现在标题里的数字（有意排除，已单列） | 3 |
| 表格行丢失（应恒为 0） | **0** |
| 代码块丢失（应恒为 0） | **0** |

「丢失」按内容核对：答案里出现的每个数字都必须仍出现在某个事实单元里。标题被有意排除（它不陈述事实），但标题里出现的数字单独计数，以便判断是否需要把含数字的标题也纳入核验。

## 6. 对 A2/A3 预算的含义

- A2 的候选预算当前按 `段数 × 3` 推导；段数上限变化后必须同步重算，否则会出现“答案能进绑定，但尾部 claim 拿不到候选”。
- Binder 要求模型对**每个** segment 返回一条记录；段数增加会同时放大输出长度、漏项/重复/格式错误的风险。
- Binder 另有 24 条证据行与输入长度约束；提高分段上限不会自动解除它们。

## 7. 结论（供裁定，不含实现）

1. 目前被挡的 13 轮答案中，段数原因 13 轮、单段原因 0 轮——两者必须分开处理。
2. 结构感知分段把总单元从 730 降到 433；标题以外的数字丢失 0 个、表格行丢失 0 行、代码块丢失 0 块，仅出现在标题里的数字 3 个（有意排除、需单独决定）；按 16 段预算可覆盖 9 / 20 轮答案。
3. 发布覆盖要求不变：不能只验证前 N 段就把整份答案标为通过；任何分段策略都必须保持“所有 factual claim 都有判定”这一条。
4. 本轮同时堵上一个覆盖漏洞：16 段以内但渲染后超过 16000 字符的 prompt 过去会被**静默截断**，等于要求模型为它没看到的尾部段落作判定；现在直接以 `answer_context_truncated` 拒绝并**不调用模型**（负控已加）。这是 fail-closed，不改变任何预算。
