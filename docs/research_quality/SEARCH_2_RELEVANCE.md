# Search-2 分析层：CJK 单字重叠 → 双字组合

> 这一层决定「哪些检索结果值得读」。Search-1 的失败案例显示它把单字词典页判成相关，
> 于是这些页面被选中、被读取、再被丢弃——既浪费读取预算，也污染上下文。

## 问题

`source_assessment._tokens()` 原来按**单个汉字**切词：

```python
_TOKEN_PATTERN = re.compile(r"[a-z0-9]+|[\u3400-\u9fff]", re.IGNORECASE)
```

后果（Search-1 真实快照，31 题）：

- 查询 `星铁 千冶·刃 遗器 推荐 黄泉队` 有 12 个 token，百度百科「星（汉语文字）」命中 1 个 → overlap 0.083
  → 判定 `weak`（0.325）→ `worth_reading=True`。
- 整个 363 条结果池里，**359 条被判为值得读（99%）**：这个打分几乎没有过滤能力。
- 实测读取这些页面的结果是 403 / 空缓存，白花一次读取。

## 改动

1. **CJK 双字组合**：CJK 连续串切成 bigram；只有一个字的串才保留单字。
   词典页与实体查询不再共享 token，除非真的有两个连续字相同。
2. **CJK 连接符归一**：`千冶·刃` / `千冶・刃` / `千冶刃` 视为同一实体（否则 `·` 会切出一个孤立单字）。
3. **英文虚词剔除**：`the/and/how/to/...` 不再参与重叠计算，避免「恰好有 the 和 of」的页面被判相关。
4. **contextual 阈值 0.75 → 0.6**：token 变成更诚实的单位后，覆盖 5/7 已是明确相关，
   旧阈值只是把「单位变少」误读成「不相关」。

## 同一快照上的测量

| 指标 | 旧（单字） | 新（双字） |
| --- | ---: | ---: |
| 池内「值得读」行数 | 359/363（99%） | **313/363（86%）** |
| 被排除的词典/百科行 | — | 13 条百度百科 + 33 条汉字站/官网首页 |
| 合并重排 top-1 变化 | — | 3 题（B02、C04、N03） |

3 题 top-1 变化全部向好：

| 题 | 旧 top-1 | 新 top-1 |
| --- | --- | --- |
| B02 星铁虚构叙事 | 星（百度百科单字） | miyoushe 黄泉队虚构叙事攻略 |
| C04 轻量化遥感变化检测 | 轻（百度百科单字） | CSDN 轻量化遥感变化检测 |
| N03 Rust tokio vs async-std | Rust 官网首页 | CSDN 两运行时对比 |

另有一处行为边界：**词面评分不再决定「能不能读」**。合法的 URL 即使 `directness=unmatched`
也仍然可读（跨语言、同义表达的情况由读取后的内容判断），评分只用于排序与分析信号。
词典页的过滤改由读取后的内容判断负责，而不是在搜索阶段直接否决。

## 局限

- 86% 仍然偏高：搜索结果池天然与查询同主题，这个分数只负责「值不值得读」，不负责排序质量。
- bigram 会漏掉同义改写（「高铁」vs「高速铁路」）；这需要语义匹配，不是字符重叠能解决的。
- 官方首页可能因不含查询词而被判不值得读——作为「读来回答问题」的候选这是正确的，
  但如果后续需要「站点身份」信号，应单独建模，而不是放宽字符重叠。
