## 2. 对照：可满足时才绑定

为排除实验接线错误，另跑 1 条最小对照：取证据正文中的**一句完整原文**作为答案（1 段），同样 3 条 read 行、同样模型与参数：

```
status = validated, claims = 0
raw = {"refused":false,"segments":[{"segment_ref":"s1","kind":"instructional","evidence_support":[]}]}
```

结论：接线、prompt、解析、发布校验全部正常工作——模型在有合法引用路径时会给记录，
在无法给出合法支持时整体拒绝。

## 3. 为什么是整体拒绝，而不是逐条判断

binder 的规则要求：

- 规则 4：每个 factual 段必须给出至少一个来自 research claim 的 `evidence_id`；
- 规则 4b：`read` 行**只有在该段完整复述原文一整句时**才能引用，改写一律会被服务端拒绝；
- 规则 6：整份答案无法安全绑定时 `refused=true`。

本次 4 轮答案都是对来源的**改写与归纳**，不是逐字复述；证据行只有 `read` 行、没有 claim 级关系。
于是模型面对的是"必须给出支持、但没有任何合法支持可给"的契约，拒绝是符合规则的唯一安全动作。

这与验收要求「无依据的支持结论 = 0」一致：**模型没有编造支持**，代价是绑定覆盖为 0。

## 4. 这说明什么

1. **当前瓶颈不是分段，也不是候选预算。** 14 单元（低于 24）同样被拒；
   降到 1 段完整原文则能通过。差别不在长度，而在"是否存在可引用的合格支持"。
2. **结构感知分段 + 24 无法单独提升绑定覆盖**：即使单元更合理、预算更宽，
   缺少 claim 级支持资格时，模型仍会（正确地）整体拒绝。
3. **A3 是前置条件，不是后续优化。** 没有"已核验片段 + 语义支持"的资格记录，
   改写型回答在 binder 里注定被拒；这也解释了过去"读到了却答不出来"的现象。
