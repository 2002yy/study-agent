# CL-M3 能力合同：模型驱动的查询规划

2026-10-23。基线 `main` = `1af25c91`（已含 `#249`、`#251`）。
本文只定义合同与验收，不含实现。

---

## 0. 结论

**Study Agent 不缺"模型自己写搜索词"的能力——旧语义研究链已经具备，而且词表不受用户原句限制。**
缺的是两件事：

1. 新对话循环（`conversation_bounded_loop`）没有接到任何搜索执行器，`ActionProposal` 也没有搜索参数位；
2. 旧链路的查询规划是**一次性预规划 + 确定性恢复**，不是"每拿到一批观察就重新开放完整规划"。

因此 CL-M3 的搜索任务不是重写研究系统，而是**把已有规划器接进新循环，并把"观察后重新规划"变成显式能力**。

### 1.1 `history_allowed` 的实际行为（修正项）

生产聊天走的是 `ExternalDataPolicyChatService`，它**覆盖**了 `start_turn`
（`policy_chat_service.py` 类内第 49 个方法），并且在该方法里显式传了历史开关：

```python
# policy_chat_service.py:513-526
web_tools = self.dependencies.resolve_web_tools(
    command.user_input,
    ...
    conversation_context=(_tool_context(command.chat_history) if decision.history_allowed else ""),
    history_allowed=decision.history_allowed,
)
```

而 `decision.history_allowed` 的默认值来自
`external_data_policy.py:59`——`normalize_cloud_context_policy(None)` 返回
`"allow_local_evidence"`，该值在 `history_allowed` 的允许集合内（`:100-103`）。
**所以默认是开启的，不是关闭。**

真正没有传该参数的是另外两条路径：

| 调用点 | 是否传 |
| --- | --- |
| `policy_chat_service.py:514`（生产聊天） | 传 |
| `chat_service.py:644`（基类路径，测试与直连用） | 不传 → 默认 `False` |
| `group_chat_service.py:195`（群聊） | 不传 → 默认 `False` |

结论：**多轮上下文搜索在生产聊天路径上默认可用**；基类与群聊路径不可用。
CL-M3 不需要"补历史开关"，只需要保证新循环把同一份 `chat_history` 按同样的策略传下去。

## 2. 两条链的能力差异（已核实）

```text
旧语义链（PersistentWebToolAgent._resolve_semantic）
  interpret(episode)  ── 一次 ──►  proposed_queries (≤3)
       │                              │
       │                              ▼
       │                     recover_public_research(query_plan=plan)
       │                       搜索 → 读取 → relevance 判定
       │                       （semantic_session 只做相关性，不再规划）
       │                              │
       └────────────── 确定性恢复规则（model_targets / recovery_budget）
                                      ▼
                                  汇总回答

新对话循环（conversation_bounded_loop）
  decide → use_tool(focus, tool) → 执行工具 → 观察回填 → 再 decide
       ▲                                                      │
       └──────────────────────────────────────────────────────┘
       每轮都重新问模型，但 tool 参数里没有"搜索词"这个位；
       也还没有任何生产搜索执行器挂在 ACTION 分发上。
```

关键差别不是"能不能自主写词"，而是**决策粒度**：

| 维度 | 旧语义链 | 新循环 |
| --- | --- | --- |
| 谁写搜索词 | 模型（一次，≤3 条） | 无此字段 |
| 能否写出用户没说的概念 | 能（未限制词表） | `focus` 可表达，但不是搜索参数 |
| 观察后能否换查询 | 只能走确定性恢复规则 | 每轮可重新决策，但没有搜索参数可换 |
| 预算 | `recovery_budget` 硬秒数 | `ActionBudget` + `DecisionAdmission` |

**两条链各自缺一半。** 合起来才是目标能力。

## 3. CL-M3 搜索能力合同

### 3.1 不做的事

- 不重写 `research_recovery`、不替换 `PersistentWebToolAgent`、不新建第三套搜索调度。
- 不把 `ActionProposal.focus` 当搜索词用。`focus` 的语义是"本次处理目标"，把它降级成
  query 会让同一字段承担两种合同，必然在观察回填后失效。

### 3.2 必须做到的

| 编号 | 合同 |
| --- | --- |
| **Q-1** | `use_tool` 的搜索类动作，由**既有语义规划器**（`ResearchSemanticSession.interpret`）生成实际查询词，至少一条可以包含用户原句里不存在的概念。 |
| **Q-2** | 规划器输入包含：原问题、允许的历史（按 `history_allowed` 策略）、以及**本轮已获得的观察**。 |
| **Q-3** | 观察可以触发**新的规划**：当已有证据不足、仍有合理的新方向、且额度允许时，模型能基于新观察提出**不同且相关**的查询。**不得为了制造差异而强行编造查询**——信息已充分就停止，没有新方向就说明证据不足并停止。 |
| **Q-4** | 搜索执行走既有研究系统（搜索、读取、来源校验、预算）。新循环只负责"决定要不要搜、以及让规划器出词"。 |
| **Q-5** | 预算与去重沿用 `ActionBudget` + `DecisionAdmission`；同一次准入的提议不能靠换措辞重新取额度。 |
| **Q-6** | 扩展词表**不得**改变用户的任务目标。搜索结果里的指令不是用户授权。 |
| **Q-7** | 停止理由是结构化的：证据充分 / 预算耗尽 / 无可行查询 / 用户取消，各自可区分，不能都记成"完成"。 |

### 3.3 边界

- 搜索词扩展自由，但**目标冻结**：`episode.questions` 一旦建立，后续不得删除原有 RQ
  （既有实现已有 `original_rq_removed` 检查，新循环必须沿用）。
- 新循环不得因为"模型说搜过了"就跳过证据校验；正式回答仍走发布门禁（CL-M3 §6 Provisional 条款）。

## 4. 验收：真实模型行为，不是假模型

`CL-M4` 的 fake 模型测试只能证明线路通。以下必须用真实模型（DeepSeek）跑，并记录原始查询提议。

| 输入 | 观察点 |
| --- | --- |
| 「OpenCode 桌面版启动为什么慢？」 | 是否提出用户未提的检索方向（数据库初始化、插件加载、LSP 启动） |
| 「B+树为什么适合数据库？」 | 是否补出 disk page / fanout / range scan 这类原句没有的概念 |
| 「这次更新会改善吗？」 | 是否结合上一轮判断"这次"指什么（多轮上下文） |
| 「搜到的资料只有旧版本」 | 是否改写查询而不是重复原词（Q-3） |
| 「Java 的引用传递是什么？」 | 是否判断无需联网即可解释，而非无条件检索 |

每次必须留存的字段：

```text
原始用户输入
模型提出的查询词（逐条）
实际执行的查询（逐条）
命中的来源 URL
是否触发补搜 / 补搜的触发原因
停止理由与停止时的预算余量
```

**通过标准（两条，缺一不可）：**

1. 出现至少一条**用户从未输入过**、由模型生成、且**确实进入了搜索工具**的查询；
2. 初次结果不足时，模型产生了**与上一轮不同**的下一条查询，而不是重复。

只满足"输出里出现了关键词"不算通过——那可能只是把用户原句抄进回答。

## 5. 尚未决定的设计问题（需在 CL-M3 动工前定）

1. **规划器放在哪一层。** 是让新循环的 `use_tool` 直接调用
   `PersistentWebToolAgent.resolve`（复用整条链，含它自己的预算），还是在循环与 recovery
   之间插一个只出词的适配器（更可控，但要重接预算）？
   前者改动小但会形成"两套预算"；后者干净但要证明与旧链等价。
2. **观察与 episode 的关系。** `ResearchEpisode` 有 `attempts` / `source_leads` 字段，
   但目前 recovery 不拿它做再规划。要让 Q-3 成立，必须明确：新循环的 observation trail
   如何写回 episode，以及写回后是否允许 `interpret` 再次生成 `proposed_queries`。
3. **两次规划的额度关系。** 第二轮 `interpret` 是一次真实模型调用，必须计入
   `DecisionAdmission`，否则"多轮规划"会变成不受控的费用增长。

## 7. 已冻结的设计裁定（2026-10-23）

用户在评审中冻结了四层能力与三项实现选择。以下为定稿，实施时不再重新取舍。

### 7.1 四层能力

| 层 | 内容 |
| --- | --- |
| 一 | 模型自主选择行动：直接回答 / 联网 / 先答再查 / 继续研究。不是程序默认每轮都搜。 |
| 二 | 模型自主制定搜索计划：复用 `ResearchSemanticSession`，允许用户没说过但相关的词，生成多条查询。 |
| 三 | 依据搜索结果重新决策：真实观察回到外层循环，模型自己判断补搜、换方向、还是结束。 |
| 四 | 受控发布与界面呈现：工具结果不直接获得证据权威，仍走原来源验证与发布合同。 |

### 7.2 三项实现裁定

| 问题 | 裁定 |
| --- | --- |
| 规划器放哪层 | **中间适配层**。不直接调用完整 `PersistentWebToolAgent.resolve()`；适配层负责出词、交给既有执行器、把观察送回新循环。 |
| 观察如何写回 | `ResearchEpisode` 保持现有字段结构，作为**规划状态投影**；真实执行日志由服务端权威记录维护。 |
| 第二轮规划费用 | 统一计入模型调用准入，并**独立计入真实费用账本**。 |

### 7.3 为什么不能直接包 `resolve()`

三条，均有代码依据：

1. `resolve()` 是一次完整的有界研究（规划 → 搜索 → 恢复 → 整理），外层无法在每次查询后插入决策。
2. 时限冲突：`LoopLimits` 默认 `timeout_seconds=30.0`、`action_timeout_seconds=5.0`
   （`conversation_bounded_loop.py:42-45`），而旧研究本身就要 30/60 秒量级，内层另有
   `configured_completion` 的独立语义调用。包进去必然外层先超时、内层还在跑。
3. 语义调用不走新预算：`configured_completion` 直接调 `src.llm_client.chat`，
   `max_tokens=1400`、`request_max_retries=0`（`semantic_recovery.py:181-187`），
   不受 `DecisionAdmission` 约束。

### 7.4 规划会话不能复用（新发现）

`ResearchSemanticSession.request()` 的实现是：

```python
if stage in self.stages or len(self.stages) >= 3:
    raise ValueError("semantic_call_limit")     # semantic_recovery.py:205-206
```

同一 `stage` 不能执行第二次，且总数上限 3。因此**不能对同一个 session 连续调用两次
`interpret()`** 来实现重新规划。合同要求：

- 每个规划轮次创建**新的受控会话**，但沿用同一个权威 `ResearchEpisode`；
- 会话身份由「操作 ID + 研究轮次 + 规划阶段」派生，保证稳定、可去重；
- 由统一准入层预留与结算，不依赖进程内计数器。

### 7.5 观察上下文会被主动丢弃（新发现）

`episode_context()` 在序列化超过 `CONTEXT_CAP` 时，按顺序降级：

```python
context["history_snippets"] = ""
context["episode"]["attempts"] = []
context["episode"]["source_leads"] = []
context["omitted"] += ["history_snippets", "attempts", "source_leads"]   # :171-175
```

即：**观察可能根本到不了下一轮规划**。合同要求适配层显式处理这种降级——
要么在预算内保住关键观察，要么在 `omitted` 标注后接受"无观察规划"，
不得假设 `attempts` / `source_leads` 一定可读。

另外：`attempts` 上限 8、`source_leads` 上限 5（`:85`、`:91`），
它们是有界规划上下文，不是审计日志。

### 7.6 `original_rq_removed` 校验的位置

该约束不在 `ResearchDecision.parse()` 里，而在 `_resolve_semantic()` 对后续决策的处理中
（`persistent_web_agent.py:507-512`）。**绕开 `resolve()` 不等于绕开它**——
适配层必须自己复刻这条检查，否则目标冻结（Q-6）在新链路上失守。

### 7.7 新增硬约束

| 编号 | 合同 |
| --- | --- |
| **Q-8** | 查询规划与执行分层：适配层出词，执行器搜索，两者不互相内嵌。等价性验收是「相同输入 + 固定模型返回 → 一致的合法查询计划与来源资格判断」，不是关键词文本相同。 |
| **Q-9** | 停止条件与搜索同等重要：证据充分 / 无新方向 / 额度耗尽 / 用户取消，四种必须可区分。**不得把系统变成无休止的决策循环。** |
| **Q-10** | 费用双轨：逻辑额度（决策/规划/判断/生成次数）与真实费用额度（已提交给 DeepSeek 的调用及其预留）分开记账。超时、取消、断网**不自动退还**预留。 |
| **Q-11** | `conversation_action_dispatch` 按 `ConversationAction` 注册，不按 `proposal.tool` 名注册（`conversation_bounded_loop.py` 的 `handlers: Mapping[ConversationAction, ActionHandler]`）。因此 handler 必须用**已验证的 `proposal.tool`** 找到真实执行器，并二次检查权限、预算与参数。禁止把所有 `USE_TOOL` 无条件导向联网搜索，也禁止"工具名存在就执行另一个工具"。 |

### 7.8 验收标识：`CL-M3-SEARCH-AUTONOMY`

| 项 | 必须可观察 |
| --- | --- |
| 隐含搜索需求 | 用户不说"联网"，模型也判断需要查 |
| 自主关键词 | 实际查询含用户未提供的合理概念 |
| 多查询规划 | 围绕不同子问题生成不同查询 |
| **观察驱动补搜** | 第一次查询后的新信息**真正影响**第二次查询 |
| 无需搜索 | 稳定的知识问题能直接回答 |
| 权威与预算 | 新增搜索不绕过费用、来源资格、取消与发布规则 |

第四项是核心：不是"预规划三条依次执行"，而是新信息改变了下一步。

## 9. 时间预算（2026-10-23 冻结）

### 9.1 现状核实

三条主张全部成立，且比描述更严格。

| 主张 | 证据 |
| --- | --- |
| 单次决策 5 秒 | `conversation_decision_runner.py:29` `DecisionLimits.timeout_seconds = 5.0` |
| 单次动作 5 秒、整轮 30 秒、最多 4 次 | `conversation_bounded_loop.py:42-45`：`max_decisions=4`、`timeout_seconds=30.0`、`action_timeout_seconds=5.0` |
| `answer_then_research` 两阶段共用一个动作窗口 | `conversation_action_dispatch.py:162-166` 把该动作展开为 `(ANSWER, USE_TOOL)` 两阶段，`:186` 串行执行，两个阶段的超时判断都对比**同一个** `started` 与 `timeout_seconds`（`:174`、`:208`） |
| 新传输非流式 | `conversation_deepseek_transport.py:74` `"stream": False` |

所以「先答 3 秒、剩 2 秒给搜索」不是推测，是当前实现的直接后果。
并且**有 SSE 不等于逐 token**：正文在一次请求完成后才作为完整事件输出。

### 9.2 硬上限（改配置改不动的地方）

`LoopLimits.__post_init__` 自带校验：`max_decisions` 1–8、`timeout_seconds ≤ 120`、
`action_timeout_seconds ≤ 30`（`:49-55`）。`DecisionLimits.timeout_seconds` 上限 30。

含义：

- 单动作调到 15–30 秒**在校验范围内**，不需要改合同；
- 整轮要超过 120 秒、或单动作要超过 30 秒，**必须改校验本身**，那是一次合同变更，不能当配置项处理。

### 9.3 冻结三原则

| 原则 | 内容 |
| --- | --- |
| **P-1 动态分层** | 普通聊天不为研究付延迟；复杂搜索获得合理空间。不允许全局一个数字。 |
| **P-2 分阶段独立限时** | 初步回答不得占光搜索时间；内层研究预算与外层循环预算共享**同一个**截止时间，不是各拿一份。 |
| **P-3 分开验收** | 首个有用回答时间、最终完成时间、超时率、费用、答案质量分别测量，不合并成一个"延迟"指标。 |

### 9.4 建议初始预算（工程起点，非实测值）

| 场景 | 总时限上限 | 体验目标 |
| --- | --- | --- |
| 普通聊天 / 教学 | 20–30 秒 | 尽快直接回答 |
| 简单联网 Lookup | 45–60 秒 | 尽早给出有用信息 |
| 多次检索 Standard | 90–120 秒 | 持续提供有内容的阶段更新 |
| 深入研究 Deep | 独立、可取消的持久任务 | 研究与聊天并行 |

内部阶段拆分：

| 阶段 | 初始上限 |
| --- | --- |
| 模型初次决策 | 5 秒 |
| 初步回答生成 | 8–12 秒 |
| 单次搜索/读取动作 | 15–30 秒 |
| 观察后重新规划 | 5 秒 |
| 最终答案生成 | 12–20 秒 |
| 最终收束预留 | 约 10 秒 |

规则：每阶段取「自身上限」与「外层剩余时间」的较小值；未用完的时间顺延给下一阶段，
但任何阶段都不得突破整轮截止。

### 9.5 对应的结构要求

**搜索必须拆成能交还观察的独立动作**，不能把整段 60 秒 Standard 研究藏进一个 `USE_TOOL`。
只有这样做，30 秒的动作上限才够用；否则只能改上限，而那会连带改变 `answer_then_research` 的
两阶段窗口语义。

同时，`answer_then_research` 的两阶段必须**各自计时**。当前共用一个窗口的实现，
在 CL-M3 接线前需要明确：是拆成两次独立 dispatch，还是给第二阶段一个显式顺延额度。
这不改 `#252`–`#255`（它们不含这段逻辑），但必须在 M3-QC 之前定。

### 9.6 验收指标

| 指标 | 要求 |
| --- | --- |
| 首个有用回答时间 | 真实模型测量，3–5 秒是目标而非承诺；**不得用"正在搜索"状态回执充数** |
| 最终完成时间 | 按场景分层记录，不跨场景平均 |
| 超时率 | 分类统计（决策超时 / 动作超时 / 整轮超时） |
| 费用 | 与 Q-10 的真实费用账本对齐 |
| 答案质量 | 与延迟分别评价，不用速度掩盖质量下降 |

### 9.7 与 CL-M1 的关系

**CL-M1 的时间默认值不改。** 现有 4 次决策 / 30 秒 / 5 秒适合有界模块与离线验证，
不是最终联网产品的配置。改它属于 CL-M3，且要先满足 §9.5 的拆分前提。

## 10. `CL-M3-RESEARCH-LIFECYCLE`：长时自主研究

2026-10-23 冻结。与 `CL-M3-SEARCH-AUTONOMY`（§7.8）配套：一个管"会不会自己查"，一个管"能不能查得久"。

### 10.1 现有代码能撑多久（核查）

`LoopLimits.__post_init__` 的硬校验（`conversation_bounded_loop.py:49-55`）：
`max_decisions` 1–8、`timeout_seconds ≤ 120`、`action_timeout_seconds ≤ 30`。

**结论：把一轮循环扩到 30 分钟不是改配置能实现的。** 必须保留单轮有界执行器，
另设长时协调器。

### 10.2 可复用的范式（初步核查）

`DeepTriggerRunner`（`src/application/deep_trigger.py`）已经实现了长时任务的核心形状：

| 能力 | 实现 |
| --- | --- |
| 周期推进 | `_run()` 每 `interval` 扫一次，`wake()` 可即时唤醒 |
| 启动恢复 | `_run()` 先做一次 "Immediate recovery scan"，重启不等第一个间隔 |
| 幂等扫描 | `scan_once()` 按状态取批：ARM → PENDING → PUBLICATION，每批限量 |
| 无长连接 | 状态在库，扫描推进；不要求一条 HTTP 请求存活全程 |

**但它的状态机是为 Deep 续写定制的三态**，不是通用的"研究轮次"。所以：

- **范式可复用**：状态机 + 周期扫描 + 启动恢复扫 + 限量批处理；
- **状态机需扩展**：需要新增"轮次/检查点/信息增量"维度，不能直接把研究循环塞进
  ARM/PENDING/PUBLICATION。

这一条是 CL-M3 动工前必须验证的：**现有 Deep 基础设施能否统一承载新对话循环的研究轮次**，
还是需要并列一个研究协调器。本文不预设答案，但禁止"把 `run_conversation_loop()` 拉长到 30 分钟"这种做法。

### 10.3 五档预算（初始工程值，非实测）

| 档位 | 默认预算 | 最大硬上限 | 场景 |
| --- | --- | --- | --- |
| Fast 快速聊天 | 30 秒 | 60 秒 | 教学、普通交流 |
| Lookup 快速查询 | 90 秒 | 3 分钟 | 版本、攻略、文档查询 |
| Standard 标准研究 | 5 分钟 | 12 分钟 | 比较软件、排查故障 |
| Deep 深度研究 | 15 分钟 | 30 分钟 | 技术调研、多来源验证 |
| Extended 扩展研究 | 30 分钟 | 60 分钟 | 大型项目分析、跨文档研究 |

**上限不是目标。** Standard 给 12 分钟，模型在第 70 秒证据已足就必须在第 70 秒结束。

### 10.4 内层分层

| 层级 | 建议初始上限 |
| --- | --- |
| 单次模型决策 | 5–15 秒（按实测调） |
| 单次搜索请求 | 10–30 秒 |
| 单次页面读取 | 10–30 秒 |
| 单次规划循环 | 60–120 秒 |
| Standard 整体 | ≤ 12 分钟 |
| Deep 整体 | ≤ 30 分钟 |
| Extended 整体 | ≤ 60 分钟 |

每轮内部循环结束即保存状态，由协调器决定是否开下一轮——
不必把搜索、分析、回答全塞进一次 `run_conversation_loop()`。

### 10.5 多维预算（时间之外）

时间放宽到一小时后，时间本身不再能防失控。起始配置（需实测校准）：

| 维度 | 起始上限 |
| --- | --- |
| 模型调用 | 60 次 |
| 自主搜索 | 40 次 |
| 网页读取 | 80 次 |
| 研究决策 | 30 次 |
| Token | 按档位设上限 |
| 真实费用 | 独立账本，与 Q-10 对齐 |

**四个维度必须同时受控。** DeepSeek 的费用不只取决于次数——60 次短调用与 60 次长上下文调用
可能差一个数量级。只限次数不限 token 等于没限。

### 10.6 六条核心要求

| # | 要求 |
| --- | --- |
| **R-1** | 五档预算可显式选择；模型可在授权范围内**建议**升档，但不能自行升。 |
| **R-2** | 单轮循环截止 ≠ 研究结束。协调器可继续下一轮。 |
| **R-3** | 研究不因聊天切换、页面刷新、普通 SSE 断连而丢失。只有用户明确取消或政策终止才结束。 |
| **R-4** | 每次迭代必须有信息增量。连续无进展、来源重复、预算耗尽时停止。**禁止为耗满时间而循环。** |
| **R-5** | 阶段性结论与正式结论分离：研究中可以显示发现，未验证内容不得获得发布权威。 |
| **R-6** | **禁止静默升级费用预算。** 从 Standard 升 Deep 必须经用户授权与费用准入。 |

### 10.7 与实施阶段的关系

| 阶段 | 时间策略 |
| --- | --- |
| CL-M1 / CL-M2 | 继续用当前短时配置完成合并与生产接线。**不动 `LoopLimits`。** |
| CL-M3 | 支持持久、可取消、可恢复的分钟级研究 |
| CL-M4 | 研究过程显示在聊天界面，允许继续对话与补充条件 |
| CL-M5 | 真实模型与真实请求测量速度/成本/质量，再校准各档上限 |

### 10.8 验收

`CL-M3-RESEARCH-LIFECYCLE` 的通过条件（与 §9.6 的指标合并使用）：

1. 一次 Standard 研究跨越多轮循环，中途断开 SSE 后重连能看到已完成轮次；
2. 用户取消后不再产生模型调用（有账本证据，不只是状态字段）；
3. 连续两轮无信息增量会自行停止，而不是跑满 12 分钟；
4. 升档必须留下用户授权记录；
5. 研究期间可以继续普通聊天，两者互不阻塞。

**一句话**：不要让为保护普通聊天而设的 30 秒超时，成为整个研究能力的天花板。

## 11. QD-3d：终止与授权的三项语义（2026-10-24 冻结）

§10.6 的 R-3、R-4、R-6 在 QD-3a～3c 落地后仍是空的。本节把它们写成**可执行的判定**，
每条都带**判据**（怎么算满足）与**反例**（怎么算违反），以便负控测试能直接照着写。

本节只定义语义，不含实现，也不含任何真实模型调用。

### 11.1 R-3：协作式取消

**裁定**：取消是**协作式**的。先把取消状态**持久化**，再禁止任何新的外部请求。
不采用"立刻 SIGKILL 执行进程"——它无法保证 §10.8 第 2 项「取消后不再产生模型调用」，
因为被中断的请求可能已经到达服务端并且已经计费。

**沿用既有范式**：`cancel_requested_at` 时间戳 + 状态转换，与
`learning_closure_repository` 的取消写法一致。取消**不新增第二套取消机制**。

**时序（这是本条的全部内容）**：

1. 用户取消 → 原子写入 `cancel_requested_at` 与 `status='cancelled'`；
2. 执行器在**发起任何新的模型调用之前**检查该字段；
3. 已取消 → 不再发起调用，落盘为已取消，**保留已有观察与未解决问题**。

**边界（用户 2026-10-24 明确）**：

- 正在进行的外部调用可以**尽力**中断，但**不得假定网络中断意味着服务端未执行、未计费**。
- 取消之后**不得**：提交新请求、升档、发布过期结果。
- 已发生的费用预留按既有合同处理（#259 账本），本节不另设结算规则。
- 取消**不得**抹掉已完成轮次的观察（与 R-4 的"保留成果"同理）。

**判据**：取消落盘后，执行器在下一轮发起调用前读到 `cancel_requested_at` 即停止。
**反例**：取消落盘后仍发起一次模型调用；或取消抹掉了已完成轮次。

### 11.2 R-4：有效信息增量

**裁定**：以**新观察 / 新证据**计数为准，但**新观察不等于有效增量**。

**关键限制（用户 2026-10-24 补充）**：不能简单用"搜索结果数量增加了"判定增量。
连续两轮搜索、同一网页被重复读取，即使产生两个读取事件，也不构成有效增量。

**计入增量的三种情形**：

1. 新增**此前未掌握**、且与当前任务**相关**的观察或证据；
2. 新证据使原有结论**得到支持 / 产生冲突 / 解决缺口**；
3. （由 1、2 派生的）新证据进入持久化的观察集合。

**不计入增量**：重复读取同一来源、仅措辞变化、空结果、没有新内容的执行状态。

**判定主体**：信息增量**由执行器依据实际记录确定**，**模型不能自行声明成功**。
即：判据基于已持久化的观察集合（`observation_urls` / `evidence`）的**去重差集**，
而不是模型输出里的一句"我找到了新东西"。

**判定单位**：以**完整研究迭代**为单位，不要求搜索、阅读等每个原子动作都立即产生证据。
一轮结束后若**没有**有效增量，则**停止当前自动迭代**。

**停止的语义（重要）**：停止的是**自动迭代**，不是判整个研究失败。
已有成果与未解决问题**必须保留**。状态是 `stopped` 而非 `failed`，
`stop_reason` 记为「无信息增量」。

**判据**：连续两轮有效增量为零 → 自停，不跑满时长。
**反例**：把"本轮执行了 N 个动作"当作增量；把重复读取计入增量；
无增量时把研究标成 `failed` 而丢掉已积累的证据。

### 11.3 R-6：独立持久授权表

**裁定**：升档授权是**用户权限决策**，与 `quota_observed`（额度**观察**）性质不同，
**不得混用**，必须用**独立持久表**。

**两类记录**：

| 记录 | 内容 |
| --- | --- |
| **升档请求** | 操作身份、当前档位、目标档位、原因、拟增加的费用/调用额度 |
| **授权决策** | 关联请求、批准或拒绝、授权范围、时间、有效期、费用上限 |

**状态机**：`pending → approved / denied / expired`。
**状态只能经由明确的用户动作转换** —— 没有用户动作，就停在 `pending`。

**升档前必须重新核验**（不是"请求过就行"）：

- 授权记录存在，且状态为 `approved`；
- 授权**未过期**；
- 授权关联的**操作身份**与当前研究一致；
- 授权的**费用/调用上限**足以覆盖这次升档。

**一律不得升档的情形**：超时、取消、被拒绝、记录缺失。

**与事件日志的关系**：事件日志**可以**记录审计过程（谁请求了、谁批了），
但**不能代替**权威授权记录。这与 §32.4「事件表不是第二个真相」是同一条纪律。

**判据**：没有 `approved` 的授权记录时，任何代码路径都不得把 tier 改掉。
**反例**：把请求本身当作批准；用 `quota_observed` 承载授权；
授权过期后仍按它升档；把"上一轮升过档"当作本轮的授权。

### 11.4 与既有代码的关系

| 既有物 | 3d 的关系 |
| --- | --- |
| `ResearchStopGate`（既有停止决策表） | **不改**。3d 的终止**策略**在它之外一层：它答"这一波是否可结算"，3d 答"这个研究是否还要继续"。两者不重叠。 |
| `learning_closure_repository` 的 `cancel_requested_at` 范式 | **沿用**。不新造取消机制。 |
| `research_states.quota_observed` | **不动**。它仍是额度观察，授权另立表。 |
| `research_events`（QD-3c） | **只记审计**，不作权威授权来源。 |
| `ResearchRound.observation_urls` / `evidence` | **增量判定的数据来源**（去重差集）。 |

### 11.5 本节明确未宣称

- §10.8 五项验收**仍然一项都没完整通过**。第 2 项需要真实账本证据，第 3、4 项需要 3d 实现，
  第 1、5 项已在数据与语义层具备条件但需真实模型的多轮研究。
